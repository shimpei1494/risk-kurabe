開発中はAIと一緒にADRを30本書いていました。この記事では、そのADRを読み返しながら、当時の自分の判断を振り返ります。

# ハッカソンで作ったもの

## きっかけ：災害リスクを「比べる」のは意外と大変

近年、地震や水害などの自然災害のニュースが多いと感じています。引っ越し先を検討するときなど、その地域の災害リスクを知りたい、他の地域と比較したいというニーズがあるのでは？と考えました。

しかし、実際には次のような課題があり、災害リスクを比較するのは難しいと感じました。

- 洪水と地震で、見るべきサイトやデータが違う
- 自治体ごとにハザードマップの見せ方が違う
- 1地点ずつ調べることはできても、**複数の候補地を同じ条件で見比べる**のは難しい

「もっと気軽に、同じものさしで見比べられたらいいのに」と思ったのが出発点です。

## TOKYOりすくらべ でできること

住所検索か地図から **1〜3地点** を選ぶと、次の情報を同じ画面で比較できます。

- 関東1都6県の **洪水浸水想定（想定最大規模）**
- 東京都内では、**地震時の総合危険度・建物倒壊危険度・火災危険度**

地図上で指標を切り替えて確認でき、わかりにくいところは **表示中の公開データだけを使って** AIに質問できます。出典や公式ハザードマップへのリンクもあり、「詳しく調べる前の入口」として使えるアプリを目指しました。

入力欄は最初は1つだけで、比較したくなったら地点を足していけます。結果の地図では、地図上の好きな場所の値を確かめたり、ピンを少し動かしてその場で判定し直したりもできます。

使ったオープンデータは主に次の2つです。

| データ | 提供元 |
| --- | --- |
| 洪水浸水想定区域（想定最大規模） | 国土交通省・国土地理院（ハザードマップポータルサイト） |
| 地震に関する地域危険度測定調査（第9回） | 東京都オープンデータ |

# どう取り組んだか

何を作るかは、使えそうなオープンデータをAIに調べてもらい、壁打ちしながら考えました。いくつか案を出した中で、最後は「自分が欲しいと思えるアプリ」を基準に、構想を練りました。

## grill-with-docs で「質問攻め」にあいながらADRを書く

作るものが決まっても、すぐには実装に入りませんでした。まず [grill-with-docs](https://github.com/mattpocock/skills) というAgent Skillを使って、AIに **徹底的に質問してもらう** ところから始めました。

grill-with-docs は、ざっくり言うと「計画や設計の曖昧なところを、AIが容赦なく質問して詰めていく」スキルです。答えて決まったことは、その場で **ADR** と **用語集（CONTEXT.md）** に書き残していきます。

実際に聞かれたのは、たとえばこんなことです。

- 対象地域は全国にするのか、東京だけにするのか
- 住所検索で出た座標が実際の建物とずれていたらどうするのか
- ピンが浸水区域の境界ぎりぎりにあったら、どちらの値を出すのか
- AIに「この地点はおすすめ」と言わせてよいのか
- 東京都外の地点で、東京都の地震危険度はどう表示するのか

どれも、実装の途中で気づいていたら手戻りになっていた論点です。

ADRは日本語のタイトルで、1つの判断につき1ファイルです。中身は「コンテキスト」「決定」「結果」の3つに分けています。後から判断を変えたときは、古いADRを消さずに「ADR-0016により置換」のように状態を書き換えて残しました。

用語集では、「比較地点」「地点調査」「地点判定」「境界警告」などの言葉を、このアプリの中での意味として定義しました。ADR・コード・テスト・画面の文言、そしてAIへの指示まで、同じ言葉で揃えられたのは大きかったです。

開発期間は2週間でしたが、実際に手を動かしたのは8日ほどです。初日にgrill-with-docsで設計を詰めてADRを25本作り、残りの日でAIと一緒に実装していきました。

## ADRがAIのガードレールになった

実装は基本的にはすべてAI（Codexデスクトップアプリ）にやってもらいました。

主な設計の判断はADRに書かれているので、AIに「ADR-0002に沿って境界警告を実装して」のように指示できます。AIが勝手に「周辺の最大値を出す」といった別の仕様を作ってしまうことが減りました。ADRの「結果」の欄には「テストにはこのケースを含める」といった実装上の影響まで書かれているので、そのままチェックリストとしても使えました。ADRで決めたこと（判定不能と区域外を分ける、AIに住所を渡さない、など）はテストでも確認しているので、AIに大きめの変更を頼むときも安心でした。

# ADRを読み返す

ここからが本題です。30本のADRを読み返してみると、多くの判断が「**何を守るか**」という同じ問いにつながっていました。その中から特に大事だった4つを紹介します。

## ① ADR-0022 → 0026：「データがない」を「安全」と誤解させない

> 東京都外の地点はランクへ変換せず、データ状態を`対象外`とする。
> ランク1を`安全`、ランク5を絶対的な`危険`または被災確率として表現しない。

このアプリでいちばん気をつけたのがここです。「値がない」ことには種類があり、区別せずに見せると「何も出ていない＝安全」と誤解されてしまいます。

| 表示 | 意味 |
| --- | --- |
| 区域外 | データはあるが、その地点は浸水想定区域などに含まれていない |
| 対象外 | そもそもその指標の対象地域ではない（例: 東京都外の地点の東京都地震危険度） |
| 判定不能 | データの取得に失敗したなどの理由で、判定できなかった |

東京都の地震危険度のランクも、都内の町丁目どうしの相対評価なので、ランク1を「安全」、ランク5を「危険」とは書きません。終盤に東京都の「総合危険度」を主な表示にしたとき（ADR-0026）も、洪水まで含めた独自のスコアに見えないよう「東京都・地震時の総合危険度」と表記しています。

> 🖼 【画像TODO】比較表で「区域外」「対象外（東京都のみの指標）」が並んでいるスクリーンショット。東京都内と都外（例: 神奈川県）の地点を比較している状態がわかりやすい。

## ② ADR-0002 → 0030：データを丸ごと変えても、方針は残った

> 確定したピン地点の値を主結果として表示する。
> 境界警告によって主結果を周辺の最大値に置き換えない。

浸水想定区域の境目では、ピンが少しずれるだけで結果が変わります。そこで、周辺の最大値ではなくピンの一点の値を結果にしつつ、半径25m以内に別の区分があれば「境界付近です」と警告することにしました。

ところが開発終盤、自前で加工していた洪水データでは、公式のハザードマップと一致しない地点があるとわかります。そこで、洪水の判定を公式の統合タイルを使う方式へ丸ごと切り替えました（ADR-0027、0030）。

それでも、「ピンの一点を結果にする」「25mの境界警告」「区域外と判定不能を分ける」といった方針は、そのまま引き継げました。データの扱い方ではなく「ユーザーに何を見せるか」をADRで先に決めておいたからだと思います。

## ③ ADR-0009 → 0023：AIには判断させない

> 「安全」「危険」「おすすめ」「住むべき」などの居住判断を結論として示す。（← 禁止）
> 独自の総合順位またはスコアを作る。（← 禁止）

AIに自由に書かせると、「この地点は安全です」「こちらがおすすめ」のような、データにない判断を言ってしまうおそれがあります。そこで、AIには公表された値や区分を比べることだけを許し、居住判断や独自のスコアは禁止しました。AIに渡すのも画面に表示中のデータだけで、**住所や座標は渡していません**（ADR-0008、0009）。

回答の見せ方は、当初は開発時間を優先してプレーンテキストに決めていました（ADR-0023）。ただ、このADRには「将来はOpenUIで表示したい」ことと、導入するときに守る条件（読み取り専用の部品に限る、任意のURLやコードは生成させない）まで書いてありました。そのおかげで、終盤に余裕ができたとき、迷わず OpenUI に移行できました。

## ④ ADR-0025：守るものを決めたら、削る順番も決まる

> 次の機能と品質要件は最後まで削減しない。
> - 1地点の調査と、最大3地点への段階的な比較
> - `区域外`、`未公開`、`対象外`および`判定不能`の区別
> - 指標ごとの半径25m境界警告
> - 出典、データ基準時点および注意事項

1人・2週間のハッカソンで、期限直前に場当たり的に機能を削ると、信頼性に必要な部分まで欠けかねません。そこで実装前に、削る順番と最後まで削らないものを決めておきました。「削らないもの」には、①と②で守ると決めたものがそのまま並んでいます。

## 方針を変えたADRの一覧

ADRは一度書いたら終わりではありません。開発を進めるうちに、いくつかの判断を変えています。置き換えたADRも消さずに残しているので、**「なぜ今こうなっているのか」だけでなく「なぜ一度は別の選択をしたのか」** までたどれます。

| 当初の判断 | 変更後 | 理由 |
| --- | --- | --- |
| ADR-0001: MVPを全国対応にする | ADR-0016: 関東1都6県に絞る | 1人・2週間で全国分のデータを扱うと、中心機能の完成を妨げるため |
| 頻度別の浸水データも表示する | ADR-0027: 頻度別の浸水データを削除 | 収録されている水系が限られ、「データなし」ばかり並んでしまったため（②） |
| 都県別の洪水ポリゴンを自前で加工して判定 | ADR-0030: 公式の統合タイルに移行 | 自前のデータだけでは、公式サイトの表示と一致しない地点があったため（②） |
| ADR-0023: AIの回答はプレーンテキストで表示 | OpenUI の部品で表示 | 比較結果をリッチな見た目で伝えたくなったため（③） |

# ADRに残らなかったこと

ADRは「判断」を残すものなので、触りながらの細かな改善や開発環境づくり、ブランドのことはADRにはなっていません。ここでは、ADRには書かなかったけれど、こだわったことを紹介します。

## ADRで骨組みを作り、触りながらUXを磨く

UXの大きな方針は、最初にADRで決めていました。入力欄を1つから始めること（ADR-0012）、住所候補を選んだら確認なしで地点を確定すること（ADR-0006）、地図に出す指標は1つだけにすること（ADR-0020）などです。

ただ、ADRで決めた仕様どおりに作っても、それだけで満足いくUXにはならなかったので、実際に画面を触っては気になったところをAIに直してもらう、の繰り返しです。この期間のUX改善のうち、ADRとして残したのは地図上で値を確認する・近くで再判定する機能（ADR-0029）くらいで、ほとんどはコミットにしか残っていません。

AIは、指示すればそれらしいUIをすぐに作ってくれます。ただ、操作の流れに違和感がないか、本当に便利に使えるかは、人が実際に触って確かめて初めて気づけることがまだ多いと感じました。AIに作ってもらい、人が触って気づいたことを具体的に伝えて直してもらう。この役割分担が、今回はうまくはまったと思います。

## Vite+ でAIが書いたコードを締める

AIにコードを書いてもらうと、書く速さは上がります。その一方で、品質をどう保つかが課題になります。

個人開発なので、CIまでは用意していません。それでも最低限の品質は守れるように、一定のLintと型チェックを入れ、判定ロジックやGIS処理を中心にVitestでテストを書いています。これらをローカルで手軽に回せるようにしてくれたのが Vite+ です。

### Vite+ とは

[Vite+](https://viteplus.dev/) は、開発サーバー・ビルド・テスト・Lint・フォーマット・パッケージ管理を、`vp` という1つのコマンドにまとめたツールです。

```bash
vp install   # 依存関係のインストール
vp dev       # 開発サーバー
vp check     # フォーマット・Lint・型チェック
vp test      # テスト（Vitest）
vp build     # ビルド
```

このプロジェクトでは pnpm や npm を直接使わず、すべて `vp` 経由にしています。AIエージェントへの指示を書いた `AGENTS.md` にも、次のように書いています。

> コードの修正が完了したら必ず `vp check` を実行し、エラーが出た場合はすべて修正してから作業を完了としてください。

コマンドが1つにまとまっているので、AIに「最後に何を実行すればよいか」を迷わせずに済みます。

### コミット前に自動でチェックする

`vp config` を実行すると Git のフックが設定され、コミットの前にステージしたファイルだけ `vp check --fix` が自動で走ります。設定は `vite.config.ts` に数行書くだけです。

```ts
staged: {
  "*.{js,jsx,ts,tsx,json,css}": "vp check --fix",
},
```

### Lint設定

Lint（Oxlint）の設定は、一定厳しくしています。

- 型情報を使ったLint と型チェックを有効にする
- **警告も1件あればエラー扱い**（`denyWarnings: true`）
- React・アクセシビリティ（jsx-a11y）・Promise などのプラグインを有効にする
- React 向けの診断ツール **react-doctor** のルールを Oxlint のプラグインとして組み込む

AIが書いたコードでも、機械的にチェックできるところは機械に任せる。人は設計やUXの判断に集中する、という役割分担です。

`vp check` とは別に、ときどき次の2つも実行していました。

- **fallow**: 使われていないファイル・依存関係・exportを見つける。方針転換で古いコードが残りやすかったので役に立った
- **react-doctor**: Lintのルールとは別に、コマンドとしても実行できる。プロジェクト全体を診断して0〜100点の健康スコアと課題の一覧を出し、使われていないコードも検出してくれる

# ふりかえり

## ADRを書いてよかったこと

- **4ヶ月後でも、当時の判断と理由を思い出せる。**
- **実装前に要件を固められる。** 曖昧なところを先に詰めておいたので、AIに実装してもらってからの手戻りが減った
- **AIへの指示がぶれにくくなる。** 「ADR-0002に沿って」と言えば済む
- **「やらないこと」と「いつかやること」を残せる。** OpenUI への移行がスムーズだった

特に、仕事では当然後から参画してくる人や担当の変更もあるので、過去の意思決定がドキュメントとして残っていることは非常に心強いと思いますし、自分自身そういうドキュメントを残していけるようにしたいと思いました。

## AIに任せたこと、人が決めたこと

AIに任せてよかったのは、設計の論点出しとADR・用語集への記録、実装、テスト、Lintエラーの修正、公開データの調べものです。

一方、人が決めるべきだったのは、どこまで作るかと削る順番、「安全と誤解させない」のようにユーザーの受け取り方に関わる判断、そして実際に触ってみての操作感です。AIの生成結果をそのまま使わず、画面を触りながら具体的に直してもらうことを繰り返しました。

また、TanStack Start・Cloudflare・Mantine・Vite+ といった、実装前のベースとなる技術選定も概ね自分で行いました。AIには、決めた技術の使い方を調べたり、その上で実装したりする部分を任せています。

## ハッカソンの結果

結果として、TOKYOりすくらべはファイナリストに残ることはできませんでした。

[ファイナリストの作品](https://odhackathon.metro.tokyo.lg.jp/collection/?year=2026&isFinalist=true&page=1)を見て、足りなかったと感じたのは次の2点です。

- **データの組み合わせによる驚きが足りなかった。** りすくらべは、データを見やすく、比べやすくしたところで止まっていました。ファイナリストには、水道の水質データからコーヒーの淹れ方を導くなど、データを組み合わせることで「こんなこともできるのか」と思わせる作品が多くありました
- **課題の掘り下げが浅かった。** 自分自身、ハザードマップなどから災害リスクを分析した経験が少なく、そのノウハウが足りていませんでした。ファイナリストの作品は、誰がどんな場面で困るのか、それをどう解決するのかがよく練られていました

ADRのおかげで、設計を丁寧に詰めることはできました。ただ、ADRは「何を作るか」をどこまで尖らせるかまでは教えてくれません。そこは、作る前に課題そのものをもっと深く調べておくべきだったと感じています。

# おわりに

ハッカソンは時間が限られているので、つい「とにかく手を動かす」になりがちです。今回は最初にAIと一緒に論点を出し切ってADRにしたことで、実装の判断に迷う時間が減り、終盤に焦って大事なところを削ることもありませんでした。

そして4ヶ月経った今、ADRは当時の自分の考えを教えてくれる記録になっています。AIに実装を任せるほど、「何を作るか」「何を守るか」を言葉にして残しておくことの価値は上がると感じています。

## TanStack Start：画面とサーバー処理を1つのプロジェクトに書く

[TanStack Start](https://tanstack.com/start) は、TanStack Router をベースにしたReactのフルスタックフレームワークです。型安全なルーティングに加えて、SSRやサーバー関数を使えるので、画面とサーバー側の処理を1つのプロジェクトにまとめて書けます。

住所検索の Yahoo!ジオコーダAPI と、AIの説明に使う Cloudflare AI Gateway は、どちらも認証情報が必要です。そこで、この2つだけをサーバー関数にして Cloudflare Workers 上で動かし、認証情報はブラウザに出さないようにしています。

個人的に気に入っているのは、サーバー関数の扱いやすさです。Next.js の App Router では Server Components が基本で、`'use client'` でクライアント側とサーバー側のコンポーネントを分けながら書く必要があります。TanStack Start は SSR とハイドレーションが基本で、Server Components は任意で使う位置づけです。サーバー関数は、普通のコンポーネントから import して関数のように呼べます。どこまでがサーバーで動くのかを意識する範囲が「サーバー関数の中だけ」に限られるので、理解しやすいと感じました。

型安全な点も活かせています。サーバー関数は入力をスキーマで検証していて、呼び出す側でも引数と戻り値に型が付きます。また、比較画面で選んでいる指標は URL のクエリで管理していて、ルート側で検証した値を型付きで受け取っています。

## Cloudflare Workers / R2：無料枠で動かし、ローカルでも同じように開発する

アプリは Cloudflare Workers、GISデータは Cloudflare R2 に置いています。どちらも無料枠があり、このアプリは今も無料の範囲で運用できています。R2はデータの取り出し（転送量）に料金がかからないので、GISデータをブラウザへ直接配信する今回の構成と相性が良かったです。

ローカル開発のしやすさもよかった点です。Cloudflare の Vite プラグインを使うと、`vp dev` で起動した開発サーバーの中で、本番と同じ Workers のランタイムでサーバー側の処理が動きます。認証情報も `.dev.vars` というファイルに置くだけで、本番の Secret と同じように読み込めます。

## GISの判定はブラウザでやる（ADR-0019）

地点の判定（その座標がどの浸水区分・どの町丁目に入るか）は、サーバーではなく **ブラウザで** 実行しています。

- 公開データなので、判定ロジックやデータをサーバー側で隠す必要がない
- 判定のために住所や座標をサーバーに送らなくて済む
- ブラウザ用とサーバー用でGISの処理を二重に実装しなくて済む

ただし、大きなGISデータを丸ごとダウンロードさせるわけにはいきません。そこで、**必要な範囲だけを取得できる** 形式を選びました。

- **東京都の地域危険度**: 町丁目ごとのデータを **FlatGeobuf** に変換して R2 に置き、HTTPのRange要求で必要な部分だけを取得します。地図表示用には **PMTiles** を使っています。
- **洪水**: ハザードマップポータルサイトの **公式統合ラスタタイル** を使っています（ADR-0030）。ブラウザでタイルの画素の色を読み取って、公式の凡例どおりの浸水深区分に変換します。周囲25mの画素も調べて、区分が変わる場合は境界警告を出します。

知らない色が出てきたときに、近い区分へ勝手に丸めないようにしているのが小さなこだわりです（テストでも確認しています）。

## OpenUI：AIの出力を「決めたUI部品」に閉じ込める

Generative UI は、AIが回答の内容に合わせて、表やカードなどの画面の部品を組み立てて表示する考え方です。[OpenUI](https://www.openui.com/) はそのためのフレームワークで、AIに使ってよいコンポーネントの一覧を渡し、AIが返した OpenUI Lang という記述を React で描画します。

Generative UI と OpenUI については、こちらの記事で詳しく紹介されています。

[https://zenn.dev/peishim/articles/37ff4d894f8fbc:embed:cite]

このアプリでは、AIが使える部品を次のような **読み取り専用のコンポーネント** に限定しています。

- `AssistantSummary`（要約）
- `RiskComparison`（地点間の比較）
- `RiskFact`（個別の事実）
- `AssistantNote`（注意事項）
- `HazardMapLinks`（公式ハザードマップへのリンク）
- `EvidenceFooter`（根拠・出典）

AIが任意のHTMLやURLを出力できないので、見た目はリッチでも、表示できる内容はアプリ側で決めた範囲に収まります。AIが使えないときや出力がおかしいときは、あらかじめ用意した説明文に切り替えて表示します。

## Mantine：便利なUIコンポーネントで、UI実装を省力化する

[Mantine](https://mantine.dev/) は、120以上のコンポーネントとフックがそろったReactのUIライブラリです。部品の種類が多いので、作りたい機能に合うコンポーネントがたいてい見つかります。このアプリでも、比較表・カード・ドロワー・ツールチップなどをほぼMantineの部品の組み合わせで作っていて、PCでは地点を横に並べた比較表、スマホでは地点ごとのカードと、画面幅に合わせた表示の切り替えも手早く実装できました。

開発も活発で、1〜2週間に1回ほどのペースで新しいバージョンが出ています。また、キーボード操作やスクリーンリーダーにも配慮されており、作る側だけでなく、使う人にとっての使いやすさまで部品側で担ってくれるのは心強いところです。
