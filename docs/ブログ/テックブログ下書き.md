# ハッカソンで作ったもの

## きっかけ：災害リスクを「比べる」のは意外と大変

引っ越しを考えていたとき、候補地の災害リスクを調べようとして、思った以上に手間がかかりました。

- 洪水と地震で、見るべきサイトやデータが違う
- 自治体ごとにハザードマップの見せ方が違う
- 1地点ずつ調べることはできても、**複数の候補地を同じ条件で見比べる**のは難しい

「もっと気軽に、同じものさしで見比べられたらいいのに」と思ったのが出発点です。

✍️ 【要記入】（実体験があれば1〜2文。例: 候補地が何か所あって、どれくらい時間がかかったか）

## TOKYOりすくらべ でできること

住所検索か地図から **1〜3地点** を選ぶと、次の情報を同じ画面で比較できます。

- 関東1都6県の **洪水浸水想定（想定最大規模）**
- 東京都内では、**地震時の総合危険度・建物倒壊危険度・火災危険度**

地図上で指標を切り替えて確認でき、わかりにくいところは **表示中の公開データだけを使って** AIに質問できます。出典や公式ハザードマップへのリンクもあり、「詳しく調べる前の入口」として使えるアプリを目指しました。

grill-with-docs は、ざっくり言うと「計画や設計の曖昧なところを、AIが容赦なく質問して詰めていく」スキルです。答えて決まったことは、その場で **ADR** と **用語集（CONTEXT.md）** に書き残していきます。

実際に聞かれたのは、たとえばこんなことです。

- 対象地域は全国にするのか、東京だけにするのか

- 東京都外の地点で、東京都の地震危険度はどう表示するのか

どれも、実装の途中で気づいていたら手戻りになっていた論点です。

## ADR-0012：最初は入力欄を1つだけにする

**当時の決定**

> ホームの初期状態では住所入力欄を1つだけ表示する。

**なぜそう決めたか**

比較アプリなので、最初から3地点分の入力欄を並べたくなります。ですが、それだと「1地点だけ調べたい人」に「3つ入れないといけないの？」と思わせてしまいます。

そこで、トップ画面には入力欄を1つだけ置き、必要になったら「比較地点を追加」で2件目・3件目を増やせるようにしました。1地点を調べるのが最短の操作になり、比較したい人も結果画面を経由せずに最大3地点まで入力できます。

あわせて、住所検索の候補を選んだ時点で地点を確定扱いにし、「この位置で確定しますか？」のような確認ダイアログは置かないことも決めていました（ADR-0006）。気軽に比較できる体験を損なわないためです。住所の座標が実際の建物とずれることもあるので、確定後もピンをドラッグして直せるようにしています。

## ADR-0002：ピンの一点を主な結果にし、境界付近では警告する

**当時の決定**

> 確定したピン地点の値を主結果として表示する。
> 境界警告によって主結果を周辺の最大値に置き換えない。

**なぜそう決めたか**

浸水想定区域の境目にピンがあると、少し位置がずれるだけで結果が変わります。ここで迷ったのが、次の2つのどちらを結果として出すかです。

- 周辺の最大値を出す → 危険側に寄りすぎる
- ピンの一点の値だけを出す → 実際の精度以上に確実な結果だと思わせてしまう

最終的には、**ピンの一点の値を主な結果にしつつ、半径25m以内に別の区分があれば警告する** ことにしました。警告文もADRで決めています。

> この地点は区域の境界付近です。ピンの位置によって判定が変わる可能性があります。

## ADR-0022 → 0026：「データがない」を「安全」と誤解させない

**当時の決定**

> 東京都外の地点はランクへ変換せず、データ状態を`対象外`とする。
> ランク1を`安全`、ランク5を絶対的な`危険`または被災確率として表現しない。

**なぜそう決めたか**

このアプリでいちばん気をつけたのがここです。「値がない」ことには種類があり、それを区別せずに見せると「何も出ていない＝安全」と誤解されてしまいます。

| 表示 | 意味 |
| --- | --- |
| 区域外 | データはあるが、その地点は浸水想定区域などに含まれていない |
| 対象外 | そもそもその指標の対象地域ではない（例: 東京都外の地点の東京都地震危険度） |
| 判定不能 | データの取得に失敗したなどの理由で、判定できなかった |

東京都の地震危険度のランクは、**東京都内の町丁目どうしの相対評価** です。そのため、ランク1を「安全」、ランク5を「危険」とは書かないようにしました。

開発終盤の7/30には、東京都の「総合危険度」を主な表示に格上げしています（ADR-0026）。そのとき問題になったのが名前です。単に「総合危険度」と書くと、洪水も含めたアプリ独自の総合スコアに見えてしまいます。そこで、画面では **「東京都・地震時の総合危険度」** と表記し、近くに「洪水などは含まない」と常に表示することにしました。

トップ画面にも、安全・危険の判定はしないこと、「区域外」「データなし」「対象外」は安全を意味しないことを明記しています。

## ADR-0020 → 0029：地図に出す指標は1つだけ、でも値は読みやすく

**当時の決定**

> 地図上に表示する主題リスクレイヤーは常に1指標だけとする。

**なぜそう決めたか**

洪水・地震総合・建物倒壊・火災を同じ地図に重ねると、色と凡例の意味が混ざって、何を見ているのかわからなくなります。そこで、地図に表示する指標は常に1つだけにし、結果表で選んだ指標と地図を連動させました。

ところが実際に作ってみると、色と凡例を見比べるだけでは値を読み取りにくいことがわかりました。そこで7/31に、次の改善をADR-0029として追加しています。

- 各ピンの横に、その地点の区分やランクを常に表示する
- PCではホバー、スマホではタップで、地図上の好きな場所の値を確認できる
- ピンの位置を探しにくいときは、色の表示を一時的に消せる
- 結果地図のピンをドラッグして「この位置で再判定」を押すと、その場で判定し直せる（元の位置から2km以内）

再判定は、ドラッグしただけでは結果を変えず、ボタンを押したときだけ実行します。地図の色はあくまで表示用で、正式な判定は別のデータで行っているためです。

## ADR-0009：AIには判断させない

**当時の決定**

> 「安全」「危険」「おすすめ」「住むべき」などの居住判断を結論として示す。（← 禁止）
> 独自の総合順位またはスコアを作る。（← 禁止）

**なぜそう決めたか**

AIに自由に文章を書かせると、「この地点は安全です」「こちらに住むのがおすすめ」のような、データにない判断を言ってしまうリスクがあります。災害の種類をまたいでどれを重く見るかは、本来ユーザーの価値観で決まるものです。

そこで、AIには次の制約をかけました（ADR-0008、ADR-0009）。

- AIの説明は、ユーザーがボタンを押したときだけ生成する
- 同じ指標を、公表されている値や区分のまま比べることだけを許可する
- 居住判断、独自のスコア、災害の種類をまたいだ重み付け、データにない原因や確率の補足は禁止する
- AIに渡すのは画面に表示中のデータだけで、**住所や座標は渡さない**

ADRには、将来の方向性として「ユーザーが重視する条件を保存し、その条件に合う候補を、計算過程を追える形で説明する」ことも書いてあります。MVPではやらないが、いずれやりたいことを残しておけるのもADRの良いところです。

具体的な実装（OpenUI で表示できる部品を制限した話）は、「補足：技術構成のこだわり」で紹介します。

## ADR-0025：遅れたときに削る順番を、先に決めておく

**当時の決定**

> 次の機能と品質要件は最後まで削減しない。
> - 1地点の調査と、最大3地点への段階的な比較
> - `区域外`、`未公開`、`対象外`および`判定不能`の区別
> - 指標ごとの半径25m境界警告
> - 出典、データ基準時点および注意事項

**なぜそう決めたか**

1人・2週間のハッカソンでは、データの品質や互換性の問題など、予想外のことが起こります。期限直前に場当たり的に機能を削ると、データ状態や根拠の表示のように、アプリの信頼性に必要な部分まで欠けてしまうかもしれません。そこで、実装前に **削る順番と、最後まで削らないもの** を決めておきました。

削る順番は、①分析・フィードバック機能 → ②AI要約 → ③最近使った地点と共有リンク → ④広域の地図レイヤー、です。

# ADRに残らなかったこと

ADRは「判断」を残すものなので、開発環境づくりやブランドのことはADRにはなっていません。ここでは、ADRには書かなかったけれど、こだわったことを紹介します。

## 怖がらせないブランドにする

名前の「りすくらべ」には、「リスク」と「比べる」に加えて、怖さを煽らず、やわらかく見比べてほしいという意図を込めています。キャラクターのりすも、その雰囲気づくりのためです。

ブランドの方針として、炎・津波・倒壊家屋のように恐怖を強く感じさせる表現や、盾やチェックマークのように「安全を保証する」と誤解させる表現は避けると決めました。

## Vite+ でAIが書いたコードを締める

AIにコードを書いてもらうと、書く速さは上がります。その一方で、品質をどう保つかが課題になります。

### Vite+ とは

[Vite+](https://viteplus.dev/) は、開発サーバー・ビルド・テスト・Lint・フォーマット・パッケージ管理を、`vp` という1つのコマンドにまとめたツールです。

```bash
vp install   # 依存関係のインストール
vp dev       # 開発サーバー
vp check     # フォーマット・Lint・型チェック
vp test      # テスト（Vitest）
vp build     # ビルド
```

このプロジェクトでは pnpm や npm を直接使わず、すべて `vp` 経由にしています。AIエージェントへの指示を書いた `AGENTS.md` にも、次のように書いています。

> コードの修正が完了したら必ず `vp check` を実行し、エラーが出た場合はすべて修正してから作業を完了としてください。

コマンドが1つにまとまっているので、AIに「最後に何を実行すればよいか」を迷わせずに済みます。

### コミット前に自動でチェックする

`vp config` を実行すると Git のフックが設定され、コミットの前にステージしたファイルだけ `vp check --fix` が自動で走ります。設定は `vite.config.ts` に数行書くだけです。

```ts
staged: {
  "*.{js,jsx,ts,tsx,json,css}": "vp check --fix",
},
```

### Lintはかなり厳しめに

Lint（Oxlint）の設定は、かなり厳しくしています。

- 型情報を使ったLint と型チェックを有効にする
- **警告も1件あればエラー扱い**（`denyWarnings: true`）
- React・アクセシビリティ（jsx-a11y）・Promise などのプラグインを有効にする
- React 向けの診断ツール **react-doctor** のルールを Oxlint のプラグインとして組み込む

AIが書いたコードでも、機械的にチェックできるところは機械に任せる。人は設計やUXの判断に集中する、という役割分担です。

`vp check` とは別に、ときどき次の2つも実行していました。

- **fallow**: 使われていないファイル・依存関係・exportを見つける。方針転換で古いコードが残りやすかったので役に立った
- **react-doctor**: React 特有の問題をまとめて診断する

✍️ 【要記入】（実際に見つかった問題の例があれば。たとえば洪水データを公式タイルに切り替えたとき、古い判定コードが残っていないか fallow で確認した、など）

### テスト名がそのまま仕様になる

テストは Vitest（`vp test`）で、ドメインロジックやGISの判定を中心に、単体テストを54ケース書いています。テスト名を日本語にしたので、テストの一覧がそのまま仕様の一覧として読めます。

```ts
it("関東外は洪水を区域外ではなく対象外にする", ...);
it("未知色を黙って別区分へ丸めない", ...);
it("25m以内の町丁目境界で変わる指標だけを警告する", ...);
test("住所と座標をOpenUI応答へ含めない", ...);
test("IME変換中のEnterは住所検索として扱わない", ...);
```

ADRで決めたこと（判定不能と区域外の区別、AIに住所を渡さない、など）がテストで守られているので、AIに大きめの変更を頼むときも安心感がありました。

最後の「IME変換中のEnterは住所検索として扱わない」は、日本語入力で住所を確定するためにEnterを押した瞬間に検索が走ってしまう、というよくある問題への対策です。地味ですが、日本語のサービスでは大事なところだと思っています。

## TanStack Start × Cloudflare Workers：秘密情報はサーバーに閉じ込める

住所検索には Yahoo!ジオコーダAPI、AIの説明には Cloudflare AI Gateway を使っています。どちらも認証情報が必要なので、ブラウザから直接呼ぶわけにはいきません。

TanStack Start を使うと、画面とサーバー側の処理を1つのプロジェクトに書けます。認証情報が必要な処理だけをサーバー関数にして Cloudflare Workers 上で動かし、認証情報は Workers の Secret として管理しています。サーバーを自前で用意する必要がなく、個人でもほぼ運用の手間なく公開できるのも Workers を選んだ理由です。

## GISの判定はブラウザでやる（ADR-0019）

地点の判定（その座標がどの浸水区分・どの町丁目に入るか）は、サーバーではなく **ブラウザで** 実行しています。

- 公開データなので、判定ロジックやデータをサーバー側で隠す必要がない
- 判定のために住所や座標をサーバーに送らなくて済む
- ブラウザ用とサーバー用でGISの処理を二重に実装しなくて済む

ただし、大きなGISデータを丸ごとダウンロードさせるわけにはいきません。そこで、**必要な範囲だけを取得できる** 形式を選びました。

- **東京都の地域危険度**: 町丁目ごとのデータを **FlatGeobuf** に変換して R2 に置き、HTTPのRange要求で必要な部分だけを取得します。地図表示用には **PMTiles** を使っています。
- **洪水**: ハザードマップポータルサイトの **公式統合ラスタタイル** を使っています（ADR-0030）。ブラウザでタイルの画素の色を読み取って、公式の凡例どおりの浸水深区分に変換します。周囲25mの画素も調べて、区分が変わる場合は境界警告を出します。

知らない色が出てきたときに、近い区分へ勝手に丸めないようにしているのが小さなこだわりです（テストでも確認しています）。

## OpenUI Lang：AIの出力を「決めたUI部品」に閉じ込める

OpenUI は、AIにコンポーネントの一覧を渡し、AIが返した OpenUI Lang を React で描画する Generative UI のフレームワークです。このアプリでは、AIが使える部品を次のような **読み取り専用のコンポーネント** に限定しています。

- `AssistantSummary`（要約）
- `RiskComparison`（地点間の比較）
- `RiskFact`（個別の事実）
- `AssistantNote`（注意事項）
- `HazardMapLinks`（公式ハザードマップへのリンク）
- `EvidenceFooter`（根拠・出典）

AIが任意のHTMLやURLを出力できないので、見た目はリッチでも、表示できる内容はアプリ側で決めた範囲に収まります。AIが使えないときや出力がおかしいときは、あらかじめ用意した説明文に切り替えて表示します。

開発中は、AIのコンポーネントだけを確認できる開発専用ページ（AI UI Lab）を用意し、色々なパターンの見た目を確認しながら調整しました。
